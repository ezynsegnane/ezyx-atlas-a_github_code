Observation: La description du protocole dit que le paired Wilcoxon utilise
  "seed-matched differences." Pour que ces differences soient valides comme
  appariement, il faut que les memes seeds soient utilises pour toutes les
  variantes dans le meme ordre. Le CSV confirme 20 seeds (2024-2043). MAIS
  le manuscrit ne confirme nulle part que les seeds sont initialises DE FACON
  IDENTIQUE pour le training de chaque variante avant CHAQUE epoque (et non
  seulement au debut du run). En particulier, le data loader utilise une
  randomisation interne lors du shuffling du DataLoader: si le DataLoader
  n'est pas re-seede apres set_seed() au debut du run, l'ordre des batches peut
  differer entre variantes pour le meme seed si les loaders sont crees a
  des moments differents dans le code.
  VERIFICATION CODE: atlas_a_v5_multiseed_v2.py fixe le seed AVANT la creation
  du DataLoader. Donc l'ordre des batches devrait etre identique pour le meme
  seed entre variantes (car le DataLoader est cree juste apres set_seed()).
  MAIS si le code cree le DataLoader APRES avoir fait d'autres operations
  aleatoires (par exemple la split des folds), l'etat du PRNG peut differer.
Risque reviewer: "Comment garantissez-vous que les 20 seed-matched differences
  sont reellement matched -- i.e., que les batches, augmentations, et dropouts
  sont identiques pour le meme seed entre variantes?"
Action recommandee: Confirmer dans la section Seeds (Sec 5.4) que l'appel a
  set_seed(s) est effectue APRES tout calcul de splits/index et AVANT la
  construction du DataLoader, garantissant un etat identique du PRNG pour les
  trois variantes du meme seed. Ajouter une phrase: "The random state is
  re-initialised immediately before DataLoader construction, so that within-seed
  batch ordering and augmentation trajectories are identical across the three
  variants for the same seed."

PASS_05 -- [COH_05 / mask bits correction cascade] -- CRITIQUE
Observation: La correction recommandee dans PASS_02/R2C03 est de remplacer
  "their mask bits are always 1" (Section 3.3 ligne 166) par "their mask bits
  mirror the availability of the corresponding anthropometric value
  (mask__miss_height = mask__height)."
  SI cette correction est appliquee, elle CONTREDIT potentiellement la phrase
  suivante dans le meme paragraphe: "because m_h, m_w, m_bmi are derived binary
  constants, their mask bits are always 1."
  En effet, la phrase dit que les missingness indicators sont des "derived binary
  constants" -- ce qui justifierait que leurs mask bits soient toujours 1.
  MAIS le code montre que mask__miss_height = mask__height (qui peut etre 0 quand
  height est absent). La logique est:
  - Quand height est ABSENT: mask__height=0, miss__height=1, mask__miss_height=0.
    Signification: "le flag de manque 'miss__height=1' est lui-meme indisponible
    (mask=0) quand height manque." C'est contre-intuitif mais correspond au code.
  - Quand height est PRESENT: mask__height=1, miss__height=0, mask__miss_height=1.
    Signification: "le flag de manque 'miss__height=0' est disponible quand
    height est present." Correct.
  En pratique, pour PTB-XL avec 68% de manquants pour height:
  68% des records ont mask__miss_height=0 (flag de manque indisponible quand height manque).
  32% des records ont mask__miss_height=1 (flag de manque disponible quand height present).
  La description "always 1" est donc FAUSSE pour 68% des records.
  La correction "mirror the availability" est correcte par rapport au code.
  MAIS: si mask__miss_height=0 quand height est absent, alors le modele "voit"
  l'indicateur de manque miss__height=1 mais son masque=0, ce qui signifie que
  l'encodeur meta considere cet indicateur comme "indisponible". En mode anthro,
  le modele est donc AVEUGLE aux flags de manque quand les valeurs manquent.
  Cela semble contre-intuitif: si le model ne "voit" pas le flag de manque quand
  la valeur manque, comment peut-il savoir que la valeur manque?
  ANALYSE: Dans la concatenation du demo encoder input: [demo_values, demo_mask].
  Pour l'anthro encoder input: [anthro_values, anthro_mask].
  La "anthro_values" inclut [height_z, weight_z, bmi_z, miss__h, miss__w, miss__bmi].
  La "anthro_mask" inclut [mask__height, mask__weight, mask__bmi, mask__miss_h,
  mask__miss_w, mask__miss_bmi].
  Quand height est absent:
  - height_z = imputed value (median), mask__height=0
  - miss__height=1, mask__miss_height=0 (=mask__height)
  L'encodeur anthro voit: [..., imputed_height_z, ..., 1, ..., ..., 0, ..., ...]
  Avec un masque: [..., 0, ..., ..., 0, ..., ...]
  Donc TOUS les elements de anthro_values correspondant a height (height_z ET
  miss__height) ont leurs masques a 0. Le modele peut theoriquement apprendre
  que: mask=0 pour height_z ET mask=0 pour miss__height -> height est absent.
  Mais dans l'encodeur, les masques servent a "disabler" l'attention portee
  a ces features. Si les masques sont 0 pour a la fois la valeur ET le flag,
  le modele est partiellement aveugle a l'information de manque.
  IMPLICATION: La robustesse de la fusion sous masquage (Fig 4) est partiellement
  due aux missingness indicators (miss__height etc.) dans la anthro_values,
  mais ces indicators sont eux-memes partiellement "masques" (mask=0) quand
  height manque. La vraie source de robustesse sous masquage en dehors de PTB-XL
  devrait donc etre principalement le meta-dropout (qui simule l'absence
  d'anthropometrics) et les valeurs imputed (=median) plutot que les flags de manque.
Risque reviewer: "Si mask__miss_height = mask__height = 0 quand height manque,
  l'encodeur ne peut pas 'voir' les flags de manque avec un haut poids. Comment
  la fusion est-elle robuste sous masquage? Quel mecanisme permet la degradation
  gracieuse si les indicateurs de manque sont eux-memes masques?"
Action recommandee: (1) Corriger la description dans Section 3.3 pour reflechir
  la logique du code (mask__miss_height = mask__height). (2) Ajouter une explication
  dans Section 4.3 / 4.4 que la robustesse sous masquage est principalement due
  au meta-dropout et aux valeurs imputees (median), et que les missingness
  indicators contribuent seulement quand les anthropometriques sont presentes.
  (3) Reconnaitre ce point dans les Limitations comme une subtilite architecturale.
